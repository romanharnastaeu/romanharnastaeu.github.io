Private-source project · Technical case study

VeriGoods

A mobile-first product lookup and recommendation platform that turns barcode or name searches into category-aware food and beauty-care guidance while treating missing or uncertain data as an explicit product state.

01 · Challenge

One search, several kinds of uncertainty.

A scanned code is only the beginning of a useful product answer. Product identifiers can be malformed, external records can be incomplete, food and beauty products require different evaluation logic, and two users may care about different product attributes.

VeriGoods addresses that sequence as a connected system: validate the input, locate and classify the product, run the appropriate evaluation path, incorporate user preferences and return a structured result that can also explain when the available data is insufficient.

Engineering principle: an incomplete upstream record should not be converted into a confident recommendation. Insufficient-data and error states are part of the response contract.

02 · Architecture

A category-aware data path.

The client coordinates search, result, profile, favourite and history experiences. Supabase Auth establishes user identity; PostgreSQL stores application data; Edge Functions and REST-style workflows provide a controlled boundary around data lookups and evaluation.

External data is input, not the final decision

Product records from external APIs are classified and routed into separate food or beauty-care handling. The application then combines the usable product fields with its own database-backed user context before producing a result.

03 · Product workflow

From lookup to recommendation.

01

Capture the query

The user searches by product name or submits a scanned barcode from the mobile-first interface.

02

Normalize the identifier

GTIN handling removes avoidable formatting differences and validates the identifier before an external lookup is attempted.

03

Classify the result

The workflow distinguishes food from beauty-care data so the next step uses the appropriate domain logic.

04

Evaluate available evidence

Food evaluation and beauty ingredient-risk screening operate as separate paths and can return insufficient-data states.

05

Apply user context

Profiles and preferences support dynamic recommendations, while favourites and scan history make results useful beyond one session.

06

Support administration

A separate admin application provides an operational surface for database-backed workflows.

04 · Engineering decisions

Boundaries that keep the product understandable.

  • Normalize before lookup

    GTIN rules are applied before external requests so invalid identifiers fail early and predictable variants resolve consistently.

  • Separate category logic

    Food evaluation and beauty ingredient screening remain distinct instead of forcing unlike domains into one scoring path.

  • Return structured states

    JSON responses distinguish usable results, upstream failures and insufficient evidence for safer client rendering.

  • Keep user data durable

    Supabase-backed profiles, preferences, favourites and history support personalized workflows across sessions.

  • Isolate external providers

    Open Food Facts, Open Beauty Facts and other product-data APIs are treated as integrations behind the application workflow.

  • Share a cross-platform foundation

    React Native, Expo and Expo Router support a mobile-first application with a web deployment path.
